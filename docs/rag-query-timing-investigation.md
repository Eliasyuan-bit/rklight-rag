# RAG 查询内部耗时排查（USB 问题）

测试问题：`FT 测试中 USB 错误是为什么？`。板端 LightRAG `1.5.7`，单客户端、流式回答、Rerank 开启，Naive 与 `mix` 使用相同查询参数。数据为 2026-09-21 的诊断复测；板端系统时钟显示 2026-04-28，与主机日期不一致。

## 结论

- 原始 Naive 样本的同次测试差额是 **735.0 ms**：`3799.2 - 30.6 - 235.2 - 2798.4`。原记录只有网关调用时长，没有每个 LightRAG 阶段的时间戳，不能对那次 735 ms 作精确事后分摊。
- 两次在 LightRAG 重启后的 Naive 首轮复测，都看到向量库查询阶段约 **422 ms**；其中 Embedding 网关调用约 **26 ms**，其余约 **396 ms** 在 LightRAG 调用 Embedding 前后、向量库查询返回之前。首轮日志出现 `Embedding func: 1 new workers initialized`；后续同一问题的该段降到约 **75–114 ms**。这支持“首轮工作队列/检索路径初始化或加载”是大头，但尚未把约 396 ms 精确分到队列初始化与向量库计算。
- `mix` 的图/向量搜索到候选合并，在关键词缓存命中的 5 次复测中约 **176–219 ms**；未命中关键词缓存的相近问法中约 **175 ms**。其中仍包含 Embedding 和文本检索，不是纯图遍历耗时。`mix` 中约 690–980 ms 的上下文整理阶段，几乎全部由 Rerank 网关调用解释。因此当前证据不支持“额外 700 ms 是图检索”的判断。

## Naive 重启首轮的分解

一次重启首轮的端到端耗时为 **3515.5 ms**。按 LightRAG 内部打点与网关调用记录分解如下；内部时间戳与客户端时钟均为同一板端单调时钟，约有数毫秒观测误差。

| 项目 | 耗时或时间点 |
| --- | ---: |
| 请求到 LightRAG `naive_query` 开始 | 约 43 ms |
| 向量库查询完成 | 查询开始后 422.5 ms |
| 其中 Embedding 网关调用 | 25.8 ms |
| 向量库查询中除 Embedding 以外 | 约 396.7 ms |
| 词法融合 | 57.4 ms |
| token 预算计算 | 28.1 ms |
| 候选处理（含 Rerank） | 234.8 ms，其中 Rerank 网关 222.1 ms |
| 引用与提示词组装 | 约 0.2 ms |
| LLM 分发到实际开始消费流 | 约 47 ms |
| 回答 LLM 网关调用 | 2683.2 ms |
| 模型调用以外的端到端差额 | `3515.5 - 25.8 - 222.1 - 2683.2 = 584.4 ms` |

这次复现的 **584.4 ms** 与历史 **735.0 ms** 不是同一次测试，不能直接替代历史数值。它表明历史差额可能有类似首轮初始化成分，但历史原始记录缺少阶段时间戳，无法证实历史 735 ms 的每一项。

## 口径与后续

为了获得可比的完整路径，后来临时关闭 LLM 缓存，Naive 与 Mix 各先预热 1 次、再各测 5 次。Naive 的总耗时、TTFT、模型调用外耗时中位数依次为 **2906.7 / 1447.8 / 149.1 ms**；Mix 为 **4005.0 / 2861.4 / 210.9 ms**，且每次均实际调用查询理解 LLM 和回答 LLM。逐次数据见[无 LLM 缓存 JSON](../evals/three-docs-v1/results/qa-usb-warm-uncached-timing-20260921.json)及[主对比表](rag-naive-vs-mix-performance.md)。测试结束后已恢复 LLM 缓存默认开启状态。

此前还记录了一组缓存态后续请求：Naive 4 次的总耗时/TTFT/模型调用外耗时中位数为 **2859.1 / 1396.0 / 137.0 ms**；Mix 5 次为 **3058.5 / 1912.4 / 166.7 ms**。Mix 的查询理解 LLM 在这组中均命中关键词缓存，不能解释为完整无缓存 Graph RAG 性能；仅作[缓存态 JSON](../evals/three-docs-v1/results/qa-usb-warm-timing-20260921.json)留存。

网关 `elapsed_ms` 不包括 LightRAG 端的队列等待、向量数据库处理、词法融合、token 预算、引用处理和流转发。`mix` 的 `_build_context_str` 阶段包含 Rerank，所以不能把整段算成图检索。重复测试还会命中关键词或 Rerank 缓存，冷/热结果应分别报告。

诊断探针为 `core/lightrag-extensions/install_lightrag_query_timing_probe.py` 与 `install_lightrag_vector_timing_probe.py`；请求端观测脚本为 `evals/three-docs-v1/probe_qa_timeline.py`。探针记录 `RK_QUERY_TIMING`，板端原文件备份为 `operate.py.before-rk-query-timing-probe`，第二次细分前备份为 `operate.py.before-rk-vector-timing-probe`。测试结束后，板端 `operate.py` 已从最初备份恢复、校验哈希一致，并重启 LightRAG；探针只用于诊断，不属于正常部署脚本。
