# UCM630x 两问题 RAG 性能评估（Qwen3.5-2B）

## 1. 评估范围

本报告只评估当前板端的 Qwen3.5-2B，不包含 Qwen3.5-4B 和 RKRAG。

测试文档：`UCM630x-Series-User-Manual.md`

测试问题：

1. `UCM630x 支持哪些网络模式？`
2. `呼叫队列配置流程是什么？`

对比模式：

- **Naive RAG**：原问题 Embedding，经过向量检索、BM25、RRF 和 Rerank 后生成回答。
- **Mix 请求（Text-only 路径）**：问题被识别为文档事实/配置流程类，不向回答上下文加入图实体和图关系；使用查询扩展、向量检索、BM25、RRF 和 Rerank。因此该列不能等同于传统的 Graph RAG。

测试日期：2026-09-23。Rerank 候选数为 6，`chunk_top_k=3`，单客户端串行测试。Embedding 和 Rerank token 使用 RKNN3 原生 `n_prefill_tokens`；回答 LLM token 使用模型服务返回的原生 usage。

## 2. 有效样本性能

### 2.1 问题一：UCM630x 支持哪些网络模式？

| 阶段 | Naive RAG（2B） | Mix/Text-only（2B） |
| --- | ---: | ---: |
| 查询理解 LLM | 本次未调用 | 本次未调用 |
| Embedding | 1 条 / 14 输入 token；**39.5 ms** | 3 条 / 44 输入 token；**92.0 ms** |
| Rerank | 6 个候选 / 2196 输入 token；**758.8 ms** | 6 个候选 / 2196 输入 token；**737.9 ms** |
| 回答 LLM | 1100 输入 / 28 输出 token；**1301.6 ms** | 1132 输入 / 28 输出 token；**1118.7 ms** |
| 系统首字耗时 TTFT | **2226.1 ms** | **2051.4 ms** |
| 总耗时 | **2351.2 ms** | **2177.5 ms** |
| 最终引用 | `chunk-305` | `chunk-305` |
| 答案结果 | 正确 | 正确 |

两种模式均回答“路由模式、交换机模式和双模式”，且引用 `Network Settings` 对应的 `chunk-305`。

### 2.2 问题二：呼叫队列配置流程是什么？

| 阶段 | Naive RAG（2B） | Mix/Text-only（2B） |
| --- | ---: | ---: |
| 查询理解 LLM | 本次未调用 | 本次未调用 |
| Embedding | 1 条 / 8 输入 token；**31.7 ms** | **无有效样本** |
| Rerank | 6 个候选 / 2188 输入 token；**784.4 ms** | **无有效样本** |
| 回答 LLM | 1233 输入 / 98 输出 token；**2024.2 ms** | **无有效样本** |
| 系统首字耗时 TTFT | **2040.8 ms** | **无有效样本** |
| 总耗时 | **3087.0 ms** | **无有效样本** |
| 最终引用 | `chunk-220` | `chunk-220`，但生成异常 |
| 答案结果 | 基本正确，但把 Delete 写入配置流程 | 连续重复生成，样本作废 |

Naive RAG 正确召回 `Add Call Queue` 对应的 `chunk-220`，回答覆盖了页面入口、Add/Edit、Extension、Name 和 Strategy。不过，Delete 是管理操作，不应作为配置流程步骤，因此该回答只能评为基本正确。

Mix/Text-only 同样正确召回 `chunk-220`，但回答模型连续重复“设置呼叫队列的呼叫策略”，未产生可用于性能统计的正常回答。

## 3. 作废样本记录

Mix/Text-only 下的“呼叫队列配置流程”连续重测 3 次，均生成到 512 token 上限，`finish_reason=length`。按照本次统计规则，这些结果不进入有效性能表。

| 指标 | 三次异常样本的中位数 |
| --- | ---: |
| Embedding | 3 条 / 32 输入 token；90.0 ms |
| Rerank | 6 个候选 / 2188 输入 token；783.8 ms |
| 回答 LLM | 1265 输入 / 512 输出 token；6957.0 ms |
| 系统 TTFT | 2122.9 ms |
| 总耗时 | 8113.2 ms |

这些数据仅用于说明重复生成的代价，不代表正常问答性能。

测试过程中还出现过一次 RKNN 运行时 `Alloc transfer buffer failed`。该次请求未进入统计；重启模型 Gateway、确认 LLM/Embedding/Rerank 均为 ready 后才重新采集上述数据。

## 4. 对比结论

1. 对“网络模式”这类短枚举问题，Naive 与 Mix/Text-only 都能正确回答，端到端耗时约为 2.2～2.4 秒。
2. Mix/Text-only 使用 3 条查询扩展，因此 Embedding 约 92 ms；Naive 只处理原问题，Embedding 约 32～40 ms。
3. 两种模式均向 Rerank 发送 6 个候选，Rerank 耗时约 0.74～0.78 秒，是首字前的主要固定开销之一。
4. 当前两个问题均属于文档事实/流程问题，Mix 请求没有把图实体和图关系送入回答上下文。因此，本测试比较的是 Naive 与增强 Text-only 检索路径，而不是传统 Naive 与 Graph RAG 的能力差异。
5. “呼叫队列配置流程”的重复生成不是召回失败：正确的 `chunk-220` 已进入最终证据。根因是全局提示词中两条表格格式指令与该表格上下文的组合；移除后，本轮 5 个有效样本均正常以 `finish_reason=stop` 结束。
6. 第 2 节记录的是修复前结果；修复后的同口径 5 次有效样本统计见第 6 节。当前样本可以用于单客户端延迟对比，但不能用于并发容量结论。

## 5. 正确性基准

问题一的期望答案：

> UCM630x 支持 Route、Switch 和 Dual，即路由模式、交换机模式和双模式。

问题二的期望答案要点：

1. 进入 `Web GUI > Basic Call Features > Call Queue`。
2. 点击 `Add` 新建呼叫队列，或使用 `Edit` 修改已有队列。
3. 配置 Extension、Name 等基本参数。
4. 选择呼叫策略，包括 Ring All、Linear、Least Recent、Fewest Calls、Random 和 Round Robin；默认是 Ring All。
5. 根据需要配置代理、队列长度、等待时间和失败目标等参数。

`Delete` 是删除已有呼叫队列的管理操作，不属于创建或配置流程的必要步骤。

## 6. 移除表格提示词后的两问题对比

### 6.1 测试条件

- 模型：Qwen3.5-2B。
- 查询模式：Mix 请求，两个问题均走 Text-only 检索路径。
- Rerank：6 个候选；`chunk_top_k=3`。
- 单客户端串行测试，每个问题统计 5 个有效样本的中位数。
- 查询理解 LLM：两个问题均未调用。
- 从 `RK_DEFAULT_USER_PROMPT` 中移除以下两句：

  ```text
  多型号对比优先使用紧凑 Markdown 表格。
  表格数据必须按照表头映射字段。
  ```

- “呼叫队列配置流程”首次请求只返回引用且缺少原生 usage，作为无效样本剔除，并补测 1 次。

### 6.2 中位数结果

### 6.4 差异结论

1. 两个问题使用相同的检索链路和 6 个 Rerank 候选，Embedding、Rerank 的耗时差异只有约 10～27 ms，不是总耗时差异的主要来源。
2. 呼叫队列流程问题的回答上下文多 133 个输入 token，回答多 75 个输出 token；回答 LLM 中位耗时因此增加 810.4 ms。
3. 流程问题总耗时比网络模式问题增加 757.8 ms，基本可以归因于回答更长，而不是检索更慢。
4. 网络模式问题虽然总耗时更短，但本轮 TTFT 中位数高 179.4 ms。这属于首字前执行抖动，不能解释最终总耗时差异。
5. 删除两条全局表格指令后，呼叫队列问题不再生成到 512-token 上限，正常在 103 个输出 token 结束。

原始数据位于 `evals/three-docs-v1/results/ucm630x-no-table-prompt/`。

## 7. 当前问题性能简表（2026-09-24）

### 7.1 补充图检索问题：Inbound Route 指向 Call Queue 后，来电按哪些 Strategy 分配？

该问题使用 Mix/Graph RAG。查询理解生成节点和关系后执行图检索，并与向量、BM25 文本召回结果合并。本次为设备重启后的首次查询，因此包含查询、Embedding 和 Rerank worker 的冷启动开销。

| 阶段 | Mix/Graph RAG（2B） |
| --- | ---: |
| 查询理解 LLM | 669 输入 / 54 输出 token；**1433.0 ms** |
| Embedding | 3 条 / 46 输入 token；**121.4 ms** |
| Rerank | 14 个 Chunk + 5 个证据单元 / 6756 token；**2855.2 ms** |
| 回答 LLM | 1842 输入 / 222 输出 token；**4250.9 ms** |
| 系统首字耗时 TTFT | **约 7.4 s** |
| 总耗时 | **约 10.4 s** |

Rerank 包含两级处理：第一次对 14 个完整 Chunk 排序，处理 6079 token、耗时 2589.7 ms；第二次对 5 个句子或表格行级证据单元排序，处理 677 token、耗时 265.5 ms。两项合计是模型计算工作量，不代表存在 19 个独立文档候选。

图检索初始命中 15 个实体和 24 个关系，截断后保留 8 个实体和 9 个关系；20 个实体关联 Chunk 被限制为 6 个，另有 5 个关系关联 Chunk。文本与图候选合并去重后，共有 14 个 Chunk 进入第一次 Rerank，最终回答使用 `chunk-220`。

### 7.2 问题二：呼叫队列配置流程是什么？

以下为移除冲突的表格提示词后，5 次正常样本的中位数。请求模式为 Mix，但该问题的最终回答上下文只保留文本证据，因此记为“最终仅使用文本证据”；这不表示系统跳过了查询扩展和图检索计算。

| 阶段 | Mix（最终仅使用文本证据，2B） |
| --- | ---: |
| 查询理解 LLM | 本轮未产生实际模型调用 |
| Embedding | 1 次批调用，3 条 / 32 输入 token；**90.9 ms** |
| Rerank | 6 个候选 / 2188 输入 token；**781.0 ms** |
| 回答 LLM | 1246 输入 / 103 输出 token；**2046.3 ms** |
| 系统首字耗时 TTFT | **2085.9 ms** |
| 总耗时 | **3180.0 ms** |

Embedding 的 3 条输入逐条为 8、11、13 token：第一条是原问题，后两条是 Mix 图查询使用的关键词。因此，`3 条 / 32 token；90.9 ms` 是 Mix 路径的真实测量值，不能标记为“跳过图检索”。若完全跳过图检索并按 Naive 路径执行，同一问题的实测结果为 `1 条 / 8 token；31.7 ms`，见第 2.2 节。

该问题 5/5 次均以 `finish_reason=stop` 正常结束，最终引用 `chunk-220`，未再次出现重复生成。
