# RAG 工程化修复路线图

更新日期：2026-09-18。

本文定义下一轮 RAG 工程化改造的范围、优先级、验收方式和提交边界。它以三文档
60 题评测为基线，目标是修复通用的证据链问题，**不为 USB、burn_stress、某个型号或
某一份文档硬编码答案、关键词或提示词规则**。

历史改动、现有 Hook 和早期回归记录见
[RAG 准确性回归](rag-accuracy-validation.md)与
[检索证据完整性改造记录](retrieval-hardening-plan.md)。

## 当前结论

系统已经具有基础生产 RAG 组件：Dense 检索、BM25、加权 RRF、reranker、LightRAG
图谱、文档解析、表格父子证据、局部 Evidence Refiner、引用预览及评测脚本。

因此当前问题不是“缺少一个检索模型”，而是没有形成完整的**证据闭环**：

1. 子 chunk 被召回后，相邻但不同主题的内容会一同进入生成上下文；
2. PDF 表格的标题、表头、模型行、数值可能跨 chunk，导致字段和数值失去归属；
3. 生成模型收到不完整或冲突证据时，仍可能给出貌似合理但无依据的补全；
4. 评测目前可收集回答和引用，但缺少把失败精确归类为“召回、证据、生成”的发布门禁。

2026-09-18 的三文档 60 题人工严格初审约为 **21/60**。这是当前基线，不是模型能力
上限，也不能以“HTTP 成功”或“显示了 References”替代正确率。

## 本轮范围与非范围

### 纳入范围

- 文档章节层级、父子证据和相邻证据恢复；
- 表格的标题/表头/行级检索和字段校验；
- 通用查询类型路由；
- 生成前证据完整性校验、一次定向补检索和可靠拒答；
- 可量化的 60 题回归、trace 和发布门禁。

### 暂不纳入范围

- RKNN `Alloc transfer buffer failed`、worker 重建、滚动重启等运行时稳定性问题；
- 更换 embedding、reranker、LLM 权重，或为了某题增加专用提示词；
- 以 Agentic RAG 替换全部普通查询路径。

运行时稳定性需要单独跟踪；它不能被误诊为检索质量问题。复杂规划、二次检索和验证
会增加延迟，因此只应在证据不足、跨章节或表格类问题触发，不能成为所有查询的默认路径。

## 目标架构

```text
文档 / PDF
  -> 结构解析：页码、标题路径、正文、表格、代码块
  -> 子块索引：Dense + BM25 + KG
  -> 父证据索引：章节、表格（标题 + 表头 + 全部行）

用户问题
  -> 查询类型判定（精确标识符 / 流程 / 原因 / 表格 / 比较 / 概览）
  -> 子块混合召回 + rerank
  -> 按章节或表格恢复完整父证据
  -> 证据覆盖校验 --不足--> 一次定向补检索 --仍不足--> 有依据地拒答
  -> 受限生成 + 可定位引用
```

查询类型只影响检索和证据组织，不携带任何文档名、问题答案或领域特例。

## 实施阶段

### P0：评测基线与可观测性

**目的：** 每次改动能证明它改善了哪一层，而不是只比较最终回答文案。

**状态：已完成（2026-09-18）。** 已新增证据级评测字段、交互式归因工具、基线报告和
分段结果合并工具。板端已生成
`/userdata/lightrag-data/eval-results/three-docs-baseline-60.json` 及对应报告：历史分段
结果经后续复测覆盖后为 60/60 API 正常；自动观察到预期源被引用 56/60、可见引用片段
包含所有必需摘录 24/60。这些不是语义正确率；60 题的人工失败归因仍需使用 P0 工具补齐。

#### 改动

- 固化三文档、60 题、标准答案、必需证据及当前结果快照；
- 每题写入下列字段：
  - `retrieval_hit`：正确章节/表格是否进入候选；
  - `evidence_complete`：最终上下文是否包含回答所需字段；
  - `grounded`：回答结论是否能由引用支持；
  - `answer_correct`：是否符合标准答案；
- trace 保留查询类型、候选来源、章节/表 ID、BM25/Dense/RRF/rerank 排名、最终证据 ID
  和耗时；不记录完整用户问题或完整正文；
- 输出按“未召回、上下文丢失、证据不足、生成错误”分组的 Markdown/JSON 报告。

#### 验收

- 任意失败题可被归入唯一的主要失败层；
- 60 题可重复执行并生成同一格式的报告；
- 基线报告不把 HTTP 成功率、References 数量当作正确率。

#### 建议提交

`test: add evidence-level RAG regression baseline`

### P1：章节级父子证据检索

**目的：** 消除相邻章节污染，特别是“USB 测试”答案混入 SET_PN、MaskRom、SARADC 等
后续章节的情况。

**状态：已完成首轮实现（2026-09-18）。** rerank 前会按 Markdown 标题恢复完整章节父
证据，并使用原始 chunk store 补回被 BM25 窗口裁短的正文。板端 FT02（USB）最终证据
由包含 USB/SET_PN/GET_PN 的 1151 字符 chunk 收束为仅 USB 章节的 379 字符证据；FT15
同样独立恢复 SET_PN 章节。完整 60 题回归留待 P2 与后续策略合并后执行。

#### 改动

- 入库时为每个正文子块保留 `source_file`、`page`、`heading_path`、`section_id`、
  `parent_section_id`、块序号与内容类型；
- 子块继续承担高召回；若多个命中属于同一章节，则将其聚合为章节父证据；
- 最终上下文使用“标题 + 命中子段 + 必要相邻段”，而不是按原 chunk 顺序拼接；
- 父章节超过预算时按结构裁剪，保留标题、命中点、同一列表/代码块的完整边界；
- 多章节问题允许保留多个父证据，但每个父证据必须有独立的命中理由。

#### 不做什么

- 不依据“USB”“FT”“产品号”等固定词选择章节；
- 不扩大所有问题的 token 预算；
- 不改 LLM 提示词来掩盖错误上下文。

#### 验收

- USB、SARADC、产品号类相邻章节不再互相进入最终证据；
- 流程题能保留完整步骤列表；
- 正确章节召回率不低于基线，`evidence_complete` 明显上升。

#### 建议提交

`feat: retrieve hierarchical section parent evidence`

### P2：表格行级父证据与字段一致性

**目的：** 避免性能表、量化表、型号对比表发生串行、串列、串表。

**状态：已完成首轮实现（2026-09-18）。** 表格索引继续保留“标题 + 表头 + 全部行”的
完整父证据，同时为每一行生成列名映射、规范化模型键和校验状态。查询明确到模型时，
生成前只展开匹配行；没有模型标识时仍保留完整父表。LLM/VLM/精度/服务器配置表继续
按类型隔离，避免同名模型跨表替代。

#### 改动

- 解析并存储表格标题、页码、表头、行、列、单元格、表类型和来源 chunk；
- 每行作为检索子单元，标题 + 表头 + 行作为不可拆分的生成父证据；
- 标准化模型名、版本、量化格式、数值、单位等可检索字段，但保留原文；
- 对“性能/规格/参数/对比”问题优先检索表格行；
- 生成前校验对象、指标名、数值、单位来自同一张表和同一行；
- 明确 `LLM` 表、`VLM` 表、配置表、兼容性表等类型，类型不一致不可替代。

实现文件：`core/lightrag-extensions/rk_table_parent.py`、
`build_table_parent_index.py`、`rk_lexical_retrieval.py`。本轮单元测试覆盖表格解析、
逐行字段映射、模型行筛选和父证据恢复；下一步需在板端重建索引并执行完整 60 题回归。

#### 验收

- Qwen2.5-7B、Qwen3-4B 等模型不串行；
- TTFT、TPOT、TPS 等指标不串列，且保留单位；
- 每个输出数值可定位到文件、页、表标题、表头和行。

#### 建议提交

`feat: add row-aware technical table evidence`

### P3：通用查询类型路由

**目的：** 不让所有问题以同一组 `mix` 参数和同一类证据竞争。

**状态：已完成首轮实现（2026-09-18）。** 在原有 exact/semantic/balanced 软融合基础上
增加 `table` profile：性能、规格、精度、量化和 TTFT/TPOT/TPS 等指标问题仍同时执行
向量检索与 BM25，但提高 BM25 的 RRF 权重，并沿用 exact 查询的扩大候选池和原文证据
保护。路由结果写入既有 retrieval trace，不是按文档或问题硬编码答案。

| 查询类型 | 检索重点 | 证据单位 |
| --- | --- | --- |
| 精确标识符、命令、版本、错误码 | BM25 权重提高，保留原始字符 | 命令块/命中段/同标题范围 |
| 流程、原因、介绍 | Dense + BM25 + rerank | 章节父证据 |
| 性能、规格、量化格式 | 表格行检索优先 | 标题 + 表头 + 匹配行 |
| 对比 | 分别检索每个对象，再合成 | 每对象一个完整证据包 |
| 概览 | Dense、BM25、KG 混合 | 多个去重章节 |
| 歧义、跨章节、多条件 | 先普通召回，再按缺口补检索 | 多个具名证据包 |

路由应由问题形态、实体数量、数值/单位/命令特征和初次召回证据决定。它必须可解释并输出
trace；不允许出现“某个文档必走某条路径”的规则。

#### 验收

- 同一知识库的命令、流程、表格问题显示不同且合理的检索 trace；
- 精确问题不因 Dense 相似段落覆盖原始命令；
- 普通概览问题不因路由而退化为纯 BM25。

本轮验证：`Qwen3-4B的性能数据是多少` 在板端 trace 进入 `table` profile，最终只保留
对应 LLM 表行；20 个 lexical retrieval 单元测试通过。

#### 建议提交

`feat: route retrieval by evidence type`

### P4：证据覆盖门与一次定向补检索

**目的：** 防止小模型把残缺上下文补成错误事实。

**状态：已完成首轮覆盖门（2026-09-18）。** 在证据精炼之后、生成之前，对性能/规格/
精度/量化类表格检查模型、指标和同一行校验状态；不满足条件的表格父证据会被丢弃，
避免将残缺行直接交给 2B。普通叙述证据会保留；流程、命令和对比问题会附加确定性
契约状态，缺口标记为 `needs_retrieval`，并触发一次定向 BM25 补检索。

#### 改动

- 生成前根据查询类型检查最小证据契约：
  - 步骤：存在连续步骤或完整命令序列；
  - 性能：对象、指标、数值、单位齐全；
  - 对比：每个对象都有相同维度的证据；
  - 原因：包含明确触发条件或失败判定；
  - 命令：包含原始命令或参数说明；
- 缺字段时，从缺失字段构造一次定向补检索；
- 二次检索仍缺证据时返回“当前文档未提供足够依据”，并展示实际命中引用；
- 覆盖检查优先用结构元数据与确定性字段匹配，不能再让 LLM 自己判断“是否可信”。

#### 验收

- 不包含目标对象的上下文不能生成具体数值；
- 表格题缺列名或单位时自动补检索或拒答；
- `grounded` 指标上升，幻觉型错误下降。

本轮实现：`apply_evidence_coverage_gate` 和 `apply_evidence_contract` 位于
`rk_evidence_refiner.py`，通过源策略 hook 在生成前调用；板端 Qwen3-4B 性能及
`burn_stress版本如何输出` 查询回归通过。

补检索已接入为单次 BM25 恢复，并要求补回候选再次通过同一契约后才允许进入上下文；
未通过的候选不会被强行加入。板端服务已重启，健康检查通过。

同时增加查询技术锚点过滤：当候选中存在包含问题明确标识符的来源时，降低不含该标识符
的来源冲突。该过滤保留“无锚点命中时不误删”的回退行为。

对全大写项目名或带版本/数字的显式标识符，若知识库零命中则不再用相似文档猜测，
而是进入无证据路径；该规则已加入单元测试。

#### 建议提交

`feat: gate generation on evidence coverage`

### P5：生成与引用收敛

**目的：** 让 2B 模型在已完整的证据上稳定表达，而不承担证据推理和纠错责任。

#### 改动

- 保持建库 4B、查询 2B 的模型策略；
- 建立通用回答契约：仅依据证据、数值保留对象和单位、流程使用 Markdown 列表、避免重复；
- 回答按最终证据包建立引用，引用可定位至章节或表格具体行；
- 不加入任何问题、领域或文档专用的答案文本。

#### 验收

- 输出格式与问题类型一致；
- 引用与正文结论一致；
- 不能以缩短 `max_tokens` 代替证据组织修复。

#### 建议提交

`feat: render answers from grounded evidence bundles`

### P6：回归门禁与发布

**目的：** 避免后续改动让已通过的问题退化。

#### 改动

- 保留当前 60 题作为回归集，后续扩展至 100--150 题；
- 每题保存标准答案、必需证据、允许关键点、问题类型及是否必须引用表格/命令；
- 自动输出召回率、证据完整率、引用支持率、严格正确率、TTFT、总耗时和失败率；
- 以 P0 的失败分类输出按类型的退化对比；
- 未达到阈值的改动不能更新板端默认策略。

#### 初始门槛

- 60 题无 RAG API 失败；
- 正确章节或表格召回率不少于 90%；
- 引用支持率不少于 95%；
- 严格正确率先达到 75%，再进入下一轮优化；
- 与基线相比，任何问题类型不得出现明显回归。

#### 建议提交

`test: enforce RAG retrieval and grounded-answer gates`

## 实施与验证顺序

本轮按以下顺序执行，**每完成一个功能点即测试、记录结果并单独提交**：

1. P0：基线与 trace；
2. P1：章节父子证据；
3. P2：表格行级证据；
4. P3：查询类型路由；
5. P4：证据覆盖门与一次补检索；
6. P5：生成和引用收敛；
7. P6：完整回归和发布门禁。

每一阶段至少应包含：本地单测、板端代表问题回归、60 题全量回归（或明确标记尚未
执行）、部署说明及对应 Git 提交。不能在未完成评测的情况下宣称“准确率已修复”。

## 优先处理的问题

先执行 P0、P1、P2。它们直接覆盖当前最大比例的失败：

- 相邻章节污染；
- 表格标题、表头、行被拆散；
- 目标模型或参数命中，但最终上下文缺少完整字段。

P3--P5 是在证据结构已可靠后才应叠加的控制层；若反过来先改 prompt、固定输出长度
或增加特例规则，只会掩盖问题，无法让新文档获得同样收益。
