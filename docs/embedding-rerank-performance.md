# Embedding 与 Rerank 板端性能

测试日期：2026-09-21。

测试环境：单张 RK1828，Qwen3-Embedding-0.6B 与 Qwen3-Reranker-0.6B，模型网关
单并发串行调度。每个测试点先预热 1 次，再重复 5 次。表中耗时为网关内部模型调用耗时，
吞吐按耗时中位数计算。

本节以下的批量和长度基线采集时，向量模型接口尚未返回原生 token 数，因此使用精确的
Unicode 字符数，不把字符数换算成 token。后文新增了原生计数复测。Embedding 输出
向量维度为 1024。

## Embedding：批量规模

每条输入固定为 128 字符。

| Batch Size | 总字符数 | 耗时中位数 | P95 | 客户端中位数 | 吞吐 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 128 | 28.1 ms | 28.2 ms | 31.86 ms | 35.59 条/秒 |
| 3 | 384 | 83.7 ms | 83.78 ms | 93.41 ms | 35.84 条/秒 |
| 8 | 1024 | 219.2 ms | 219.5 ms | 243.27 ms | 36.50 条/秒 |
| 16 | 2048 | 433.2 ms | 438.8 ms | 471.24 ms | 36.93 条/秒 |

该服务在本配置下基本按输入条数线性增长，没有表现出明显的批量吞吐增益。

## Embedding：文本长度

Batch Size 固定为 1。

| 单条字符数 | 耗时中位数 | P95 | 客户端中位数 |
| ---: | ---: | ---: | ---: |
| 32 | 26.3 ms | 27.26 ms | 29.54 ms |
| 128 | 28.1 ms | 28.2 ms | 31.86 ms |
| 512 | 30.8 ms | 30.88 ms | 36.03 ms |

在 32～512 字符范围内，Embedding 固定调用开销占比较高，文本长度对耗时的影响小于
批量条数。

## Rerank：候选数量

查询固定为 15 字符，每个候选固定为 256 字符。

| 候选数 | 候选总字符数 | 耗时中位数 | P95 | 客户端中位数 | 吞吐 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 256 | 35.4 ms | 35.76 ms | 36.47 ms | 28.25 候选/秒 |
| 3 | 768 | 211.2 ms | 211.4 ms | 213.03 ms | 14.20 候选/秒 |
| 6 | 1536 | 413.6 ms | 413.84 ms | 415.68 ms | 14.51 候选/秒 |
| 12 | 3072 | 824.0 ms | 826.62 ms | 825.74 ms | 14.56 候选/秒 |
| 24 | 6144 | 1648.7 ms | 1660.24 ms | 1650.70 ms | 14.56 候选/秒 |

从 3 个候选开始，Rerank 耗时与候选数量近似线性，稳定吞吐约为 14.5 候选/秒。

## Rerank：候选长度

查询固定为 15 字符，候选数固定为 6。

| 单候选字符数 | 候选总字符数 | 耗时中位数 | P95 | 客户端中位数 |
| ---: | ---: | ---: | ---: | ---: |
| 64 | 384 | 205.5 ms | 205.9 ms | 206.79 ms |
| 256 | 1536 | 413.6 ms | 413.84 ms | 415.68 ms |
| 512 | 3072 | 631.5 ms | 631.78 ms | 633.03 ms |

Rerank 耗时同时受候选数量和候选长度影响。当前实际 USB `mix` 查询对 6 个候选、
合计 3455 字符进行重排，耗时约 733.1 ms，与固定规模测试的增长趋势一致。

## 结论

- Embedding 当前稳定吞吐约为 36 条/秒，延迟主要随输入条数增长；
- Rerank 在 3 个以上候选时约为 14.5 候选/秒，并随候选文本长度继续增长；
- 控制 Rerank 的候选数和文本长度，比单独优化 Embedding 更可能降低当前查询延迟；
- 字符数只用于描述本轮输入规模。跨中文、英文和代码场景比较时，仍需向原生向量服务
  增加 tokenizer token 计数。

## 原生 token 计数复测（2026-09-21）

本节是在 Embedding/Rerank daemon 输出 RKNN3 `n_prefill_tokens`、网关透传计数后，
重新运行同一题“FT 测试中 USB 错误是为什么？”得到的**单次样本**。上面的批量与长度
测试是改造前的历史数据，仍只有字符口径；两轮耗时不可视为严格配对实验。

| 模式 | 阶段 | 输入规模 | 原生 prefill token | 网关内部耗时 | 有效输入 TPS |
| --- | --- | ---: | ---: | ---: | ---: |
| Naive | Embedding | 1 条、18 字符 | 12（逐条 `[12]`） | 30.0 ms | 400.15 token/s |
| Mix | Embedding | 3 条、48 字符 | 34（逐条 `[12, 8, 14]`） | 76.3 ms | 445.40 token/s |
| Naive | Rerank | 1 个候选、1119 字符 | 762（逐候选 `[762]`） | 226.1 ms | 3369.48 token/s |
| Mix | Rerank | 6 个候选、3455 字符 | 2340（逐候选 `[251, 621, 111, 762, 347, 248]`） | 681.4 ms | 3434.13 token/s |

这里的 TPS 是 `n_prefill_tokens ÷ 网关内部请求耗时`，包含 worker 通信、向量后处理等
开销，是**有效输入吞吐**，不是仅 NPU 计算阶段的纯 Prefill TPS。Rerank 的每个候选
token 数对应完整 Query-Document Prompt，含重复的指令、Query 和模板。Embedding 输出
仍是每条一个 1024 维浮点向量；1024 不是输出 token 数。两次 RAG 请求均命中关键词缓存，
所以 Mix 的查询理解 LLM 本轮没有再次运行。

原始记录：[Naive](../evals/three-docs-v1/results/qa-usb-naive-token-metrics-20260921.json)、
[Mix](../evals/three-docs-v1/results/qa-usb-mix-token-metrics-20260921.json)。

### 单条 1024 输入 token 的耗时

用 Qwen3-Embedding-0.6B 的 tokenizer 构造文本，板端返回的原生计数再次确认为
**1024 prefill token/条**。同一文本重复请求时，首次约 255.2 ms，后续约
38.5～39.9 ms，表现出显著的重复前缀缓存效应；不能拿重复文本的约 25.8k token/s
当作一般新文档的吞吐。再用 5 条不同前缀、均为 1024 token 的文本测试：

| 样本 | 原生输入 token | 网关内部耗时 | 客户端耗时 | 有效输入 TPS |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 1024 | 255.9 ms | 265.57 ms | 4001.48 token/s |
| 2 | 1024 | 251.9 ms | 262.31 ms | 4065.26 token/s |
| 3 | 1024 | 251.7 ms | 261.29 ms | 4067.94 token/s |
| 4 | 1024 | 251.7 ms | 261.28 ms | 4067.98 token/s |
| 5 | 1024 | 251.8 ms | 261.53 ms | 4067.09 token/s |

**中位数：251.8 ms/条，约 4067 token/s。** 这是单条、单并发、不同文本的
网关有效输入吞吐；不是纯 NPU Prefill TPS，也不能代表并发或文档长度变化后的性能。
逐次数据见 [1024-token 实测 JSON](../evals/three-docs-v1/results/embedding-1024-token-20260921.json)。
