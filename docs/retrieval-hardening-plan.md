# 检索证据完整性改造记录

## 背景与判定

2026-09-18 的三文档 smoke 评测表明，若干错误不是召回缺失：正确 PDF
chunk 已进入混合候选，但在 rerank、证据精炼或上下文打包后没有进入生成上下文。
本文将此类问题记为 **Context Loss**，并与“正确证据未被召回”的 Recall
问题分开处理。

目标不是为某份文档或某类问题硬编码答案，而是保证命令、版本、型号、表格指标等
直接事实以最小、完整、可引用的证据单元进入生成模型。

## 实施清单

| 步骤 | 改动 | 状态 | 验收方式 |
| --- | --- | --- | --- |
| 1 | 证据精炼候选改为命中优先、跨 chunk 轮转，而非按原文前 8 / 全局前 24 顺序截断 | 已完成 | 单测验证晚出现的型号表格行仍进入 reranker |
| 2 | 将表格标题/表头/命中行打包为不可拆分的表格证据包 | 已完成 | 指标问题上下文包含字段名和数值行 |
| 3 | 精确证据保护由单一 BM25 chunk 升级为覆盖核心标识符的证据单元 | 已完成 | 正确型号、命令或版本不能被泛化段落替换 |
| 4 | 生成前校验问题核心实体是否出现在最终上下文；缺失时回退或拒答 | 待实施 | 不再依据不含目标实体的上下文编造数值 |
| 5 | 运行 9 条 smoke 与 60 条评测集，记录 Recall、Context Loss、正确率、TTFT | 待实施 | 结果写入评测输出与本文件 |

## 步骤 1：候选准入修复

### 原问题

`rk_evidence_refiner.py` 原来对每个候选 chunk 只取原文顺序前 8 个证据单元，
并按 chunk 顺序在全局截断到 24 个单元。大型 PDF 或表格中，真正匹配型号的行如果
处于后部，根本不会进入 reranker；排在前面的冗余说明会耗尽预算。

### 改动

- 在调用 reranker 前，以查询中的复合标识符、ASCII 词和中文双字词给证据单元计算
  **候选准入分**；它只决定“是否有资格交给 reranker”，不代替 reranker 最终评分。
- 同一 chunk 优先提交直接命中的单元；同分仍按原文顺序，保证普通说明题行为稳定。
- 各 chunk 的候选以 round-robin 合并，避免靠前的大 chunk 吞掉全局预算。
- 命中表格行可携带既有 `table_header`，后续重建阶段仍可恢复表头。

### 边界

该步骤不改变 embedding、BM25、chunk 大小、LLM prompt 或最终生成长度；reranker
调用数量仍受原有 `RK_EVIDENCE_MAX_CANDIDATES` 限制。

### 回归用例

- 表格前有三个无关单元、`Qwen2.5-7B` 行在后部，而每 chunk 上限为两个时，目标行
  仍会进入 reranker，且输出同时保留表头；
- 全局预算为两个、存在两个 chunk 时，两个 chunk 都至少获得一个候选席位。

## 步骤 2：表格证据包

### 原问题

表格行经句子级证据精炼后，可能只留下型号和数值；字段含义位于表头，表所属场景位于
标题或紧邻 caption。小模型收到孤立行后无法判断 `162.25` 是 TTFT 还是其他指标，且
容易将同文档中其他模型的数值填入答案。

### 改动

- 证据单元保留 `heading`、`table_caption`、`table_header` 和 `table_row` 的来源关系；
- 对 Markdown 表和 JSON 表，表格前的短 caption（例如 `LLM Model Performance`）会
  随命中行保存；
- 重建最终上下文时，自动输出“章节标题 → caption → 表头 → 命中行”，同一标题、caption
  和表头只输出一次；
- 非表格段落和原始 chunk 结构不改变。

### 回归用例

对于 `Qwen2.5-7B` 性能问题，最终证据必须同时包含 `性能测试` 标题、`LLM Model
Performance` caption、`ModelName/TTFT/TPS` 表头及 Qwen2.5-7B 行，不能包含
Qwen3-4B 行。

## 追加修复：精确查询保留原始证据

步骤 1～3 的板端回归发现，部分正确 PDF chunk 已经在候选中，但 BM25 的普通
`_best_passage()` 窗口先把型号行或表头裁掉，后续保护逻辑无法识别它。另有部分精确
问题在前 6 个 fused candidate 外，导致还未进入 reranker。

追加改动如下：

- BM25 结果同时保留 `content`（聚焦窗口）和 `full_content`（原始 chunk）；
- exact 查询若聚焦窗口缺少查询标识符，使用完整原文参与重排和证据保护；
- exact 查询候选窗口从常规配置扩大到 `RK_EXACT_RETRIEVAL_CANDIDATE_K=12`，
  不改变普通语义查询的候选规模；
- 精确保护的“实质证据”判断改为基于完整内容，避免短 passage 掩盖真实表格证据。

本追加修复已通过 49 个相关单测。板端定向回归中，FT11 已能正确回答
`IS6608A=86mA`、`MPQ8655=79mA`、容差 `±20%`；这证明同一 chunk 内重复型号表
通过“按 JSON 表分组并保留表头”可以避免 ADC 数值污染电流答案。

Qwen 性能、精度和服务器配置的 4 条 PDF 指标问题仍未通过：候选中存在 PDF 片段，
但 PDF 的表头、模型行和后续说明跨 chunk 分离，且 LLM/VLM 表存在相似模型名。下一步
应建立 PDF 表格级索引（表标题/表头/行作为同一父证据），并在表类型不匹配时阻止
`Qwen3-VL` 片段替代 `Qwen3` LLM 表；本轮尚未实施。

随后发现 BM25 的 `full_content` 只有在后续 source policy 使用时才有意义；因此 source
policy 对含有明确 ASCII 标识符的查询改用完整 chunk 进行章节/表格压缩，再将最小完整
证据交给 Evidence Refiner。这样 PMIC 型号和 PDF 表格行不会被已经裁剪的 passage
覆盖掉。

## 步骤 3：精确证据保护

### 原问题

此前精确查询只保留 BM25 排名最高的一个“有正文 chunk”。这不能证明它包含用户明确
指定的对象：泛化的性能章节可能比含 `Qwen2.5-7B` 数据行的 chunk 有更高 lexical
rank，随后将正确行挤出最终上下文。

### 改动

- 从查询中通用提取复合标识符、带数字/下划线的名称、版本、CLI flag 和十六进制值；
- 对每个 rerank 候选统计这些标识符在正文中的字面覆盖数；
- 精确查询优先保护覆盖数最高的实质证据，覆盖相同才比较 BM25 rank 和初始召回 rank；
- 当问题不含这类标识符时，保持原来的 BM25 实质证据回退逻辑。

此处只保护事实对象是否真的出现于证据，未把某个型号、数字或文档名写入规则，也不
改变 reranker 的最终语义排序。

### 回归用例

一个泛化“性能说明”chunk 即使 lexical rank 第一，只要不含 `Qwen2.5-7B`，就不能
替换含模型名、TTFT、TPS 的数据行；被保护项会记录实际覆盖到的标识符，供 trace 和
后续诊断使用。
