# 板端 RAG 回归评测集 v1

本套包含 **40 题**：产线测试 16 题、ROCKRAGCLAW 部署 12 题、授权 8 题、证据不足/实时状态边界 4 题。其中 FT02 是场景不明确的部分可回答题。

依据 2026-09-15 从 162 的 ADB 板端读取的知识库原文编写。保存了原始提问的 4 题为 FT01、FT02、DEP01、AUTH01；其余是文档及历史场景衍生题，不冒充真实用户查询日志。这是已核对原文摘录的初版，尚未经过领域专家审核，也尚未执行 40 题模型基线。

## 文件

- `cases.json`：问题、必答要点、禁止断言、格式要求、来源文件、文档 ID、章节和原文摘录。
- `validate.py`：检查结构以及摘录是否存在于指定知识库；只读，不调用模型。
- `run_eval.py`：按当前板端网页参数串行调用流式查询接口，保存回答、引用原文和延迟。
- `corpus-snapshot.json`：编写时的文档内容 SHA-256，识别后续知识库版本变化。

`expected` 是验收要点，不要求逐字匹配。`forbidden` 是具体失败条件。`evidence` 是供评测者核查的证据定位，不是给被测模型的提示。章节定位仅作人工导航；没有可靠 PDF 页码的地方不编造页码。

## 如何执行一轮

1. 固定知识库版本，记录 LightRAG/网关/模型版本、查询模式、检索参数、提示词版本、输出上限。
2. 每题开启空历史会话，**仅发送 `question`**。不把 expected、forbidden 或 evidence 输入模型，也不要把评测集上传建库。
3. 先保持当前网页默认配置完整跑一轮，再一次只改一组参数或策略。FT01/FT02 为同一问题家族，汇总时同时报告家族表现，避免重复题夸大收益。
4. 保存原始回答、实际返回的引用与片段、错误/结束状态、首字和总耗时。若能取到，保存实际进入生成上下文的 chunk ID，而非仅保存最初召回结果。
5. 按下面规则人工评分。记录“未采集”与“未实现”，不要记成成功。前端有文字不等于生成正常结束。

初次建议全量 40 题。每次小改动可先跑 FT01、FT04、FT06、FT07、DEP01、DEP06、AUTH02、AUTH08、NEG01、NEG02 共 10 题，再对候选版本跑全量。

在能直接访问板端 9621 端口的机器上先跑 10 题：

```bash

```

当前 191 机器通过 162 的 ADB 访问板端时，可直接运行下面这条。脚本会临时建立 SSH/ADB 隧道，结束时自动清理：


当前脚本默认明确传入网页基线参数：`hybrid`、`top_k=6`、`chunk_top_k=3`、实体/关系/总预算 `500/300/3000`、启用 rerank。结果逐题写入 `results/`，即使中途停止，已经完成的题目也会保留。完整 40 题是串行运行，按当前单并发设备预计需要数分钟，不要同时在网页发起查询。

只跑一道接口验证题：

```bash
python3 evals/rag-v1/run_eval.py --url http://板端IP:9621 --ids FT03 --label api-check
```

这 40 题均为可见回归集，不是独立盲测集。持续根据它调参后，应从新增真实问题另建盲测集，不能只用同一批题宣称泛化提升。

## 评分规则

每题六项，分别记 0、1、2 分（语义人工判断，不用关键词出现次数代替）。证据不足题的检索项记 N/A，不纳入该项分母。

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 检索证据 | 最终上下文无有效支持片段 | 只覆盖部分要点 | 足以支持必答要点 |
| 正确性/有据性 | 核心错误或无依据确定断言 | 基本正确但有不严谨推断 | 正确且明确证据边界 |
| 完整性 | 没有回答核心问题 | 遗漏部分必答要点 | 覆盖必要要点，结尾完整 |
| 引用 | 错引、虚构引用或有依据的事实无引用 | 只有相关文件，无法定位或覆盖不足 | 引用对应支持结论的原文且可定位 |
| 格式/精确性 | 命令错误或结构严重不可读 | 基本可读但格式不满足 | 标识符精确、步骤清晰 |
| 拒答/限定 | 缺依据却断言，或有依据却无故拒答 | 说明不够清楚 | 根据 answerability 恰当回答/限定/拒答 |

对于 NEG 题，明确证据不足且没有增加外部事实，可以没有引用，引用项记 N/A。若补充文档中的排查建议，应引用支持这些建议的原文。FT02 应明确适用场景，或先询问场景并提供有条件的文档说明。

单题严格通过：所有适用项均为 2，且无 forbidden 行为。另报告各维度平均分，避免总分掩盖命令错误。可接受等价命令、参数顺序和同义表述；Linux 路径、下划线、命令参数和数字必须正确。不给答案设置统一字数或两项步骤上限。

引用指标分别记录：

- 引用支持率：实际支撑所关联结论的引用数 / 所有被核查引用数。
- 结论引用覆盖率：带有效引用的需证据结论数 / 所有需证据结论数。
- 原文定位成功率：可以定位并查看正确原文的引用数 / 尝试打开的引用数。

三项不能用“存在 References 标题”替代。没有引用时，支持率记 N/A，同时覆盖率对有事实结论的回答记 0。

本集没有穷举每题所有相关 chunks，**不能据此直接计算严格的 Recall@K**。可以先记录预期证据命中与要点覆盖；要报告 Recall@K，需补标全部相关 chunk 集合并固定分块版本。

## 结果记录

每题至少保存以下字段；建议人工评分和原始输出分开保存：

```json
{
  "run_id": "baseline-日期-配置版本",
  "case_id": "FT01",
  "question": "FT测试中USB错误是为什么？",
  "answer": null,
  "references": [],
  "final_context_chunk_ids": null,
  "ttft_ms": null,
  "total_ms": null,
  "finish_reason": null,
  "error": null,
  "cache_state": "unknown",
  "scores": {
    "retrieval": null,
    "correctness": null,
    "completeness": null,
    "citation": null,
    "format": null,
    "answerability": null
  },
  "violations": [],
  "review_notes": "待运行；null 表示未采集或未评分"
}
```

TTFT 从提交查询到第一段**答案正文**，排除状态提示、引用事件和空 SSE。它包含排队、检索等耗时，不等同模型原生 TTFT。分开报告缓存命中、非缓存查询与模型冷启动；不清空全量 LLM 缓存来制造冷测，避免影响实体抽取缓存。

汇总建议：整体与分类通过率、无证据断言数量、引用三项指标、截断/异常数、TTFT 和总耗时的中位数/P95，附样本数与缓存条件。40 题仅是初步回归样本，不能证明企业并发 SLA。

## 来源与已知风险

- USB 真正的测试条件在 `1820_test.text.md` 的 Mermaid 流程图中；只召回 KG 的“连接异常”文字不足以通过 FT01。
- 知识库技术方案文档包含旧 RAG 的生成答案展示。它们不是独立事实依据。本集 FT 题以测试说明为准，不拿旧模型答案当标准答案。
- 部署题描述 ROCKRAGCLAW/rkrag_cli，不把它的目录、接口或历史性能混同当前 LightRAG 服务。
- 授权 PDF 解析有下划线断裂和命令乱码。命令题优先使用部署指南代码。PDF 仅用于可辨识的流程、授权阶段与限制；发布前建议再用原 PDF 人工核对这些段落。
- NEG02、NEG04 检查的是静态文档不能证明当前状态/性能，不能偷偷用聊天历史或实时工具结果补答案。
- 固定来源 ID 用于定位当时的索引，评估正确引用时允许同一原始文档的等价支持片段；重新入库后 ID 变化需更新映射。

## 校验

只校验结构：

```bash
python3 evals/rag-v1/validate.py
```

对板端当前知识库做只读摘录校验：

```bash
set -o pipefail
ssh -o BatchMode=yes rockchip-yn@172.16.15.162 \
  'adb -s 32a331f9ae73952d shell cat /userdata/lightrag-data/kv_store_full_docs.json' \
  | python3 evals/rag-v1/validate.py --corpus -
```

该校验确认摘录存在并输出当前内容哈希，不代表模型答对，也不自动证明每项语义得到充分支持。将输出的 corpus_snapshot 与本目录快照对比，发现版本变化时复核预期答案和负例适用性。
